## 1. Introdução e Objetivos

### 1.1. Visão Geral dos Requisitos

A plataforma centraliza a extração, validação, padronização, consolidação e visualização de indicadores comerciais, financeiros, operacionais, de produtividade e de energia provenientes dos sistemas da Hidroforte.

Os requisitos detalhados estão em `01. PROJECT-SPEC.md` e agrupam-se em quatro capacidades arquiteturalmente relevantes:

| Capacidade                      | Requisitos          | Escopo                                                                                                                  |
| ------------------------------- | ------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Integração de dados             | `RF-001` a `RF-004` | Conectar às fontes configuradas, extrair dados, executar atualizações e registrar o status de cada execução.            |
| Processamento e consolidação    | `RF-005` a `RF-009` | Validar e converter dados para o modelo interno, consolidar fontes, sinalizar registros inválidos e preservar a origem. |
| Regras de negócio e indicadores | `RF-010` a `RF-013` | Aplicar exclusivamente fórmulas validadas, calcular indicadores e respeitar segregações definidas.                      |
| Consulta e visualização         | `RF-014` a `RF-017` | Apresentar dashboards com filtros, períodos de referência e agrupamentos.                                               |

### 1.2. Objetivos de Qualidade

Objetivos que orientam as decisões estruturais, em ordem de prioridade. Os cenários verificáveis constam na Seção 10.

| Prioridade | Objetivo         | Motivação                                                                                                   |
| ---------- | ---------------- | ----------------------------------------------------------------------------------------------------------- |
| 1          | Confiabilidade   | Garantir consistência com os indicadores oficiais e permitir auditoria de divergências pela origem do dado. |
| 2          | Manutenibilidade | Manter estrutura clara, idiomática e simples de evoluir por equipe enxuta.                                  |
| 3          | Extensibilidade  | Incorporar novas fontes e novos indicadores sem alterar integrações ou fórmulas existentes.                 |
| 4          | Segurança        | Proteger credenciais de integração e restringir o acesso conforme os perfis autorizados.                    |
| 5          | Desempenho       | Entregar consultas de dashboard e rotinas de atualização em tempo compatível com o uso operacional.         |

### 1.3. Partes Interessadas

| Parte Interessada        | Expectativa em Relação à Arquitetura                                                   |
| ------------------------ | -------------------------------------------------------------------------------------- |
| Gestão                   | Indicadores confiáveis e disponíveis para acompanhamento gerencial.                    |
| Áreas de negócio         | Fórmulas fiéis às regras aprovadas e transparência sobre a origem de cada número.      |
| Usuários finais          | Dashboards claros, responsivos e com filtros aderentes à rotina.                       |
| Tecnologia da Informação | Conformidade com políticas de infraestrutura, rede, autenticação, permissões e backup. |
| Desenvolvimento          | Arquitetura previsível para testar, manter e implantar.                                |

## 4. Estratégia da Solução

Relação direta entre os objetivos de qualidade e as escolhas estruturais adotadas:

| Objetivo / Restrição           | Estratégia Adotada                                                                                                                    | Referência           |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- | -------------------- |
| Manutenibilidade               | **Monólito Modular** em NestJS dentro de um Monorepo TypeScript, evitando a sobrecarga operacional de sistemas distribuídos.          | Seção 5, `DEC-001`   |
| Extensibilidade de fontes      | **Adaptadores isolados** por fonte externa via Injeção de Dependência (`SourceAdapter`), desacoplando extração das regras de negócio. | Seção 5.2, `DEC-004` |
| Confiabilidade dos cálculos    | **Persistência centralizada** no PostgreSQL com dados padronizados e fórmulas isoladas em **funções puras** validadas via **TDD**.    | Seção 5.2, `DEC-005` |
| Separação de responsabilidades | **Frontend desacoplado** do Backend via contratos tipados compartilhados (`packages/contracts`), sem lógica de cálculo no navegador.  | Seção 5.1, `DEC-002` |
| Previsibilidade de entrega     | Empacotamento com **Docker** e configuração externalizada por variáveis de ambiente.                                                  | Seção 7, `DEC-006`   |

## 5. Visão de Blocos

### 5.1. Nível 1 — Monorepo e Aplicações

```text
company-data-platform/
├── apps/
│   ├── api/                  # Backend NestJS (Monólito Modular)
│   └── web/                  # Frontend SPA (React + Vite)
├── packages/
│   ├── contracts/            # Tipos e contratos compartilhados entre API e Web
│   └── config/               # Configurações compartilhadas (tsconfig, lint, format)
├── infrastructure/
│   └── docker/               # Dockerfiles e docker-compose
├── docs/                     # Documentação de arquitetura e negócio
└── .ai/documents/            # Documentos vivos por entrega
```

| Bloco                | Responsabilidade                                                                                 | Regra de Dependência                                  |
| -------------------- | ------------------------------------------------------------------------------------------------ | ----------------------------------------------------- |
| `apps/api`           | Ingestão, validação, padronização, consolidação, cálculo de indicadores e API REST `/v1`.        | Pode importar `packages/*`.                           |
| `apps/web`           | Dashboards, filtros, períodos de referência e acompanhamento de status das integrações.          | Pode importar `packages/*`; nunca importa `apps/api`. |
| `packages/contracts` | Contratos de requisição, resposta e paginação entre Frontend e Backend.                          | Zero dependência de `apps/*`, ORM ou framework.       |
| `packages/config`    | Configurações comuns de compilação e estilo.                                                     | Zero dependência de código de aplicação.              |
| PostgreSQL           | Armazenamento de dados padronizados, resultados consolidados, linhagem e histórico de execuções. | Acessado exclusivamente por `apps/api`.               |

### 5.2. Nível 2 — Backend (`apps/api/src`)

O Backend segue a estrutura nativa do NestJS organizada por módulos de domínio:

```text
apps/api/src/
├── modules/
│   ├── integrations/
│   │   ├── adapters/         # Uma classe isolada por fonte externa (SourceAdapter)
│   │   ├── contracts/        # Interface SourceAdapter e StandardizedRecord
│   │   └── *.{controller,service,module}.ts
│   ├── indicators/
│   │   ├── calculators/      # Funções puras de cálculo testadas via TDD
│   │   └── *.{controller,service,module}.ts
│   ├── analytics/            # Consolidação e agregações entre fontes
│   └── dashboards/           # Consultas otimizadas e filtros para a interface
├── common/                   # Filtro global RFC 7807, interceptors de log e decorators
├── config/                   # Validação de variáveis de ambiente na inicialização
└── main.ts
```

| Módulo         | Responsabilidade                                                                                                                                             |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `integrations` | Orquestra a coleta nas fontes externas por meio de adaptadores isolados registrados via DI, valida e padroniza os registros e grava o resultado da execução. |
| `indicators`   | Concentra as fórmulas oficiais em funções puras sem dependência de framework ou banco, facilitando testes unitários diretos em TDD.                          |
| `analytics`    | Consolida e agrega registros padronizados provenientes de múltiplas fontes.                                                                                  |
| `dashboards`   | Expõe consultas filtráveis, agrupadas e paginadas para consumo do Frontend.                                                                                  |
| `common`       | Agrupa componentes técnicos transversais sem lógica de negócio.                                                                                              |

### 5.3. Nível 2 — Frontend (`apps/web/src`)

Organizado por funcionalidade (_feature-based_):

| Diretório                        | Responsabilidade                                                                            |
| -------------------------------- | ------------------------------------------------------------------------------------------- |
| `features/dashboards/`           | Páginas por categoria de indicador, cards de KPI, gráficos, filtros e hooks TanStack Query. |
| `features/integrations/`         | Visualização do status e histórico das execuções de carga.                                  |
| `shared/api/`                    | Cliente HTTP tipado com `@hidroforte/contracts` e tratamento padronizado de erros RFC 7807. |
| `shared/formatters/`             | Formatação PT-BR centralizada de moeda, volumes, percentuais e datas.                       |
| `shared/components/` e `layout/` | Componentes visuais reutilizáveis e estrutura de navegação.                                 |

### 5.4. Persistência de Dados

O PostgreSQL centraliza quatro grupos de dados:

- **Dados padronizados:** registros convertidos das fontes externas com metadados de origem.
- **Resultados consolidados:** séries e agregações prontas para consulta rápida nos dashboards.
- **Execuções de integração:** status, janela de execução, duração e resumo de falhas.
- **Registros inválidos:** inconsistências detectadas na validação para auditoria sem interromper dados íntegros.

A modelagem física definitiva e a política de retenção dependem do mapeamento das fontes em `06. DISCOVERY-BACKLOG.md`.

## 6. Visão de Execução

O acionamento dos processos de carga — manual, agendado ou híbrido — e a periodicidade por fonte serão definidos no discovery (`06. DISCOVERY-BACKLOG.md`).

### 6.1. Atualização de Dados

```text
Acionamento ──▶ IntegrationsService ──▶ Adaptador da Fonte ──▶ Extração ──▶ Validação e Padronização ──▶ PostgreSQL ──▶ Log de Execução
```

- Cada adaptador encapsula autenticação, formato de resposta e conversão para `StandardizedRecord`.
- Registros inválidos são separados e registrados sem sobrescrever o estado consolidado válido anterior.

### 6.2. Cálculo de Indicadores

```text
Gatilho / Solicitação ──▶ IndicatorsService ──▶ Leitura de Dados Consolidados ──▶ Função Pura (calculators/) ──▶ Persistência / Retorno
```

- Aplica os critérios de período de referência, agrupamento e segregação catalogados em `05. INDICATORS-CATALOG.md`.

### 6.3. Consulta de Dashboards

```text
Navegador ──▶ Frontend (React) ──▶ API /v1 (Auth + Validação) ──▶ DashboardsModule ──▶ PostgreSQL ──▶ JSON ──▶ Renderização
```

### 6.4. Comportamento em Falhas

| Situação                                    | Comportamento Esperado                                                                       |
| ------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Fonte indisponível ou falha de autenticação | Registrar falha na execução com identificação da fonte e preservar dados válidos anteriores. |
| Registro inválido ou incompleto na origem   | Registrar a inconsistência vinculada ao `externalId` e ao `executionId` para análise.        |
| Erro de persistência ou cálculo             | Abortar gravação parcial inconsistente, registrar o erro e marcar a execução como falha.     |

Diagrama lógico de implantação. Os componentes podem compartilhar servidor ou operar em nós separados conforme a infraestrutura definida pela TI.

```text
┌───────────────────┐     HTTPS     ┌──────────────────────┐     HTTPS     ┌──────────────────────┐
│     Navegador     │ ────────────▶ │  Frontend (estático) │ ────────────▶ │   Backend (NestJS)   │
└───────────────────┘               │     React + Vite     │               └──────────┬───────────┘
                                    └──────────────────────┘                          │
                                                                          ┌───────────┴───────────┐
                                                                          ▼                       ▼
                                                                   ┌──────────────┐     ┌──────────────────┐
```

- **Conectividade, hospedagem e backup:** infraestrutura final, localização do PostgreSQL, regras de rede, certificados HTTPS e rotina de backup/retenção estão rastreados em `06. DISCOVERY-BACKLOG.md`.

## 8. Conceitos Transversais

### 8.1. Padronização e Linhagem de Dados

- Dados de fontes externas são normalizados para nomes, tipos, unidades de medida e datas ISO-8601 padronizados antes da persistência.
- Todo registro ingerido preserva quatro campos mínimos de linhagem: `sourceSystem`, `externalId`, `extractedAt` e `executionId`.

### 8.2. Contratos de API e Tratamento de Erros

- Rotas versionadas sob o prefixo `/v1`, documentadas automaticamente via OpenAPI/Swagger.
- Paginação padronizada como `0-indexed` (`page=0`).
- Respostas de erro padronizadas conforme **RFC 7807 (`ProblemDetail`)**, sem exposição de stack traces, credenciais ou detalhes internos de banco em produção.

### 8.3. Observabilidade e Registros Operacionais

- Logs estruturados em JSON com correlação por `executionId` entre ingestão, validação, cálculo e erro.
- Histórico persistido de execuções contendo fonte, início, duração, volume processado, quantidade de inválidos e status final.

### 8.4. Segurança e Configuração

- Autenticação e autorização por perfil integradas ao mecanismo definido pela TI (`CON-003`).
- Variáveis de ambiente validadas na inicialização da aplicação; credenciais e segredos nunca são versionados no repositório.
- Comunicação protegida por HTTPS em homologação e produção.

### 8.5. Qualidade de Código e Testes

- Fórmulas em `modules/indicators/calculators/` são funções puras cobertas por testes unitários escritos em TDD (`RNF-005`), conferidos com massas históricas das áreas de negócio.
- Adaptadores possuem testes de integração com fixtures de respostas reais e cenários de falha.
- Regras detalhadas de lint, tipagem estrita e fluxo de entrega constam em `AGENTS.md` e `03. DEVELOPMENT-STANDARDS.md`.

## 9. Decisões Arquiteturais

### 9.1. Decisões Estruturais

Resumo das decisões vigentes. Contexto completo, análise de trade-offs e consequências constam em `04. ADR.md`.

| ID      | Decisão                                                                                           | Estado   | Justificativa                                                                                      |
| ------- | ------------------------------------------------------------------------------------------------- | -------- | -------------------------------------------------------------------------------------------------- |
| DEC-001 | Adotar **Monólito Modular** no Backend.                                                           | Proposta | Mantém separação interna por domínio com implantação e operação simples.                           |
| DEC-002 | Separar **Frontend (React + Vite)** e **Backend (NestJS)** em **Monorepo** TypeScript (`pnpm`).   | Proposta | Centraliza regras de negócio no servidor e garante tipagem ponta a ponta via `packages/contracts`. |
| DEC-003 | Adotar **PostgreSQL** como persistência centralizada.                                             | Proposta | Isola dashboards de instabilidades das fontes externas e viabiliza histórico e consolidação.       |
| DEC-004 | Usar o **padrão nativo do NestJS** com adaptadores isolados via DI e funções puras para cálculos. | Proposta | Garante SOLID nas integrações e TDD direto nas fórmulas sem a burocracia de camadas artificiais.   |
| DEC-005 | Padronizar dados antes do cálculo e restringir produção a fórmulas validadas.                     | Proposta | Evita divergências em relação aos indicadores oficiais e assegura rastreabilidade.                 |
| DEC-006 | Utilizar **Docker** para padronização de ambientes.                                               | Proposta | Garante paridade entre desenvolvimento, homologação e produção.                                    |

### 9.2. Alternativas Descartadas

| Alternativa                                      | Motivo do Descarte                                                                                          |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| Microsserviços                                   | Complexidade distribuída, latência de rede e custo operacional desproporcionais ao porte do projeto.        |
| Arquitetura Hexagonal formal em todos os módulos | Excesso de camadas, interfaces e mapeadores redundantes frente ao sistema nativo de módulos e DI do NestJS. |
| Consulta direta em tempo real nas fontes         | Acopla disponibilidade dos dashboards aos sistemas externos e impede histórico auditável.                   |
| Cálculos de indicadores no Frontend              | Fragmenta regras de negócio, dificulta testes automatizados e compromete confiabilidade.                    |

## 11. Riscos e Dívida Técnica

### 11.1. Riscos Principais

| ID      | Risco                                                              | Impacto | Estratégia de Mitigação                                                                   |
| ------- | ------------------------------------------------------------------ | ------- | ----------------------------------------------------------------------------------------- |
| RSK-001 | Atraso ou bloqueio de acesso aos sistemas de origem.               | Alto    | Mapear responsáveis e solicitar credenciais na fase inicial (`06. DISCOVERY-BACKLOG.md`). |
| RSK-002 | Regras de negócio indefinidas ou divergentes entre áreas.          | Alto    | Bloquear entrada em produção de fórmulas sem aprovação em `05. INDICATORS-CATALOG.md`.    |
| RSK-003 | Dados inconsistentes ou incompletos nas fontes externas.           | Alto    | Validar registros na ingestão e isolar inválidos sem corromper o lote válido.             |
| RSK-004 | Divergência entre indicadores da plataforma e relatórios oficiais. | Alto    | Validar fórmulas com dados históricos reais e testes unitários em TDD.                    |
| RSK-005 | Infraestrutura incompatível com a stack proposta.                  | Alto    | Confirmar hospedagem, PostgreSQL e Docker com a TI antes de finalizar a implantação.      |
| RSK-006 | Instabilidade de fontes externas durante cargas.                   | Médio   | Isolar falhas por adaptador, registrar logs e manter o último estado consolidado íntegro. |

### 11.2. Prevenção de Dívida Técnica

| ID     | Ponto de Atenção                                                | Diretriz                                                                               |
| ------ | --------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| DT-001 | Fórmulas espalhadas em controllers, SQL bruto ou Frontend.      | Centralizar todo cálculo em funções puras dentro de `modules/indicators/calculators/`. |
| DT-002 | Acoplamento das regras ao esquema de dados das fontes externas. | Converter toda entrada externa para o modelo padronizado nos adaptadores.              |
| DT-003 | Abstrações excessivas sem ganho prático.                        | Seguir o padrão nativo do NestJS e evitar camadas intermediárias sem lógica real.      |
| DT-004 | Alteração de cálculos críticos sem regressão automatizada.      | Manter TDD obrigatório para criação e manutenção de qualquer indicador.                |

## 12. Glossário

O glossário completo de negócio, dados e referências técnicas é mantido em **`07. GLOSSARY.md`**. Termos mínimos para leitura direta deste documento:

| Termo             | Definição                                                                                   |
| ----------------- | ------------------------------------------------------------------------------------------- |
| Adaptador         | Classe isolada responsável pela comunicação e padronização de uma fonte externa específica. |
| Economia          | Unidade comercial ou consumidora atendida no contexto de saneamento.                        |
| Linhagem de Dados | Rastreio da origem, do registro externo e da execução que originou um dado consolidado.     |
| Monólito Modular  | Aplicação única implantável, dividida internamente em módulos com fronteiras claras.        |
| RFC 7807          | Padrão `ProblemDetail` adotado para respostas de erro HTTP da API.                          |
| TBR               | Marcação de parâmetro ainda pendente de definição formal no backlog de discovery.           |
